## Problem Statement

Freesound holds one of the largest freely-licensed sound libraries in existence, but
getting a sound out of it and into a piece of work is a chore. A sound designer scoring a
short film, a game developer looking for a UI click, or a video editor who needs a door
creak all follow the same loop: open a browser, search, click into a sound's page, press
play, go back, try the next one, eventually log in, download a file to `~/Downloads`,
find it in Finder, drag it into the timeline, and then rename or move it so that in three
weeks it is still identifiable. Auditioning ten candidates means ten page loads and ten
trips back to the search results.

Everything about that loop is friction that has nothing to do with choosing a sound. The
comparison people reach for is Splice, where sounds are auditioned in a list and dragged
straight into the DAW — but Splice's catalogue is not Freesound's, and nothing with
Splice's ergonomics points at Freesound.

There is a second, quieter problem. Freesound's sounds carry individual Creative Commons
licenses. A CC-BY sound obliges the user to credit its author in whatever they ship; a
CC-BY-NC sound cannot lawfully be used in commercial work at all. In the browser loop the
license is at least visible on the sound's page. The moment a file lands in `~/Downloads`
that information is severed from the audio, and by the time the project is finished
nobody can reconstruct which of the forty sounds in the timeline owed a credit to whom.
A tool that makes acquisition frictionless without addressing this makes users breach
licenses faster than they could by hand.

## Solution

A cross-platform desktop application that puts Freesound behind a fast, keyboard-driven
browsing interface and lets a Sound go from search result to DAW timeline in one gesture.

The user signs in to their own Freesound Account. They search, and results appear as a
dense virtualized list with waveform, duration, author, tags and License visible without
clicking into anything. Pressing play auditions the Sound instantly via its Preview, and
in the background the Original begins downloading — so a second or two later, while the
user is still listening, the real file is on disk and can be dragged straight out of the
window into Logic, Audacity, Final Cut or any other application that accepts a file drop.
The receiving application gets the Original at its native quality, under a human-readable
filename.

Sounds worth keeping are saved to the Library with one keystroke. Sounds merely
auditioned are Staged and quietly evicted later; the user is never asked to manage this.
Library sounds can be gathered into Collections, and any Collection can produce an
Attribution Manifest — a credits document naming every author and License, and warning
about any Sound whose License forbids the use the user intends.

The License travels with the Sound from search result to Library to Manifest. It is
treated as an obligation attached to the audio, not a badge.

## User Stories

### Signing in

1. As a sound designer, I want to sign in with my existing Freesound account, so that I do not have to create yet another account for a tool that is just a view onto Freesound.
2. As a sound designer, I want to sign in through my real browser rather than a window inside the app, so that my password manager works and I can see that I am really on freesound.org.
3. As a security-conscious user, I want the app never to see or store my Freesound password, so that installing it does not widen my exposure.
4. As a returning user, I want to still be signed in when I reopen the app days later, so that I do not repeat the authorization dance every session.
5. As a returning user, I want my session to be refreshed before it expires rather than after it fails, so that I never discover I am signed out in the middle of dragging a sound into a session.
6. As a user whose session cannot be refreshed, I want to be told clearly and offered a one-click re-authorization, so that I understand what happened instead of watching downloads fail silently.
7. As a user, I want to sign out, so that I can hand my laptop to someone else without giving them access to my Freesound account.
8. As a user who has signed out, I want my Library to remain intact and playable, so that sounds I legitimately downloaded do not vanish because I ended a session.
9. As a user whose sign-in fails because the callback port is occupied, I want a specific error naming the problem, so that I can fix it rather than assume the app is broken.
10. As a user, I want to browse and audition without signing in at all, so that I can evaluate whether the app is useful before granting it access to my account.
11. As a signed-out user, I want it made obvious that downloading and dragging require signing in, so that I am not surprised when a drag is refused.

12. As a sound designer, I want to type a query and see results without pressing enter, so that browsing feels like filtering rather than submitting a form.
13. As a sound designer, I want results to keep up with my typing without firing a request per keystroke, so that the interface stays responsive and I do not exhaust my daily API allowance.
14. As a sound designer, I want to see a Sound's name, author, duration, tags, License and waveform in the result row itself, so that I can judge candidates without opening anything.

## Implementation Decisions

### Application shape

The application is Electron (ADR-0001). It is structured in three parts:

- **The core** — a plain Node module holding all behaviour: authentication, search,
  caching, the download queue, staging and eviction, the Library, Collections, and
  Manifest generation. It has no dependency on Electron and can be constructed and driven
  in an ordinary Node process.
- **The Electron main process** — a thin adapter. It constructs the core, exposes the
  core's command API over `contextBridge` IPC, and supplies the two implementations the
  core cannot provide for itself (see Boundaries). It contains no business logic.
- **The renderer** — React 19 with TanStack Virtual for windowing, Zustand for
  playback/transport state, TanStack Query for the search cache, and Tailwind. It holds
  presentation logic only and reaches the core exclusively through the preload bridge.
  `nodeIntegration` is off and `contextIsolation` is on.

Build tooling is electron-vite. Packaging, signing and notarization are electron-builder.

**The core's command API is the IPC contract.** Adding a capability means adding a command
to the core; the bridge forwards it verbatim. This equivalence is deliberate and is what
makes the testing strategy below possible — it must not be eroded by putting logic in the
main-process adapter or by letting the renderer reach past the bridge.

### Boundaries

The core depends on exactly two injected collaborators, and no others:

- **`FreesoundGateway`** — everything that crosses the network to Freesound or to the
  token Worker. Search, sound metadata, preview streams, Original downloads, token
  exchange and refresh. All HTTP lives behind it.
- **`DragHost`** — the single call that hands a file path and drag icon to the operating
  system. In production it wraps `webContents.startDrag`; it exists as a named boundary
  so that what the app hands to the OS is observable.

SQLite and the filesystem are *not* abstracted. The core talks to both directly, and
tests supply real temporary instances of each.

### Persistence

SQLite is authoritative for all organisation (ADR-0002). Downloaded Originals live in a
flat, app-managed directory named by Freesound sound id. Broad schema shape:

- **sounds** — Freesound metadata mirrored locally: id, name, author, License, duration,
  tags, format, sample rate, channels, preview URLs, waveform image URLs. Present for
  both Staged and Library sounds.
- **library_entries** — the user's intent to keep a Sound, plus their own overlay: custom
  name, custom tags, date saved. Absence of a row means the Sound is at most Staged.
- **collections** and **collection_members** — many-to-many; no nesting, no ordering.
- **staged_entries** — last-accessed timestamp and byte size, for LRU eviction.
- **peaks** — computed waveform peak data, stored as a blob, keyed by sound id.
- **search_cache** — query parameters to result page, cached indefinitely and keyed by
  the full query.
- **auth** — the encrypted refresh token blob and access token expiry.

Every downloaded Original is written with a sidecar JSON file carrying its Freesound
metadata, author and License. **The sidecar is mandatory**: it is the sole mechanism by
which the Library can be rebuilt if the database is lost (ADR-0002), and a rebuild
command exists that reconstructs `sounds` and `library_entries` from the directory alone.
Custom names, custom tags and Collection membership are not recoverable this way; that
loss is accepted.

The database is never touched on the renderer's thread, and long operations — peak
computation, rebuild, bulk eviction — run off the main thread.

### Authentication

Authorization code grant against Freesound, with no PKCE available (ADR-0004). The app
opens the system browser, catches the code on a one-shot loopback listener bound to a
fixed port, and posts it to a stateless Cloudflare Worker that holds `client_secret` and
performs the exchange. The same Worker performs refreshes. It stores nothing.

The refresh token is encrypted with Electron's `safeStorage` and written to the app's
user data directory. `keytar` is not used.

Refresh is proactive, scheduled ahead of the 24-hour expiry, and backed by a 401
interceptor that refreshes once and retries the original request exactly once. A failed
refresh transitions the app to signed-out and surfaces a re-authorization prompt; it never
retries in a loop.

Search and preview playback use token authentication and work while signed out. Only
downloading — and therefore staging and dragging — requires OAuth.

### Search and caching

Search goes from the client directly to Freesound. Every request asks for the complete
field set needed to render a row, so a result page costs exactly one request regardless
of page size and no per-Sound detail request is ever made.

Input is debounced before a request is issued. Result pages are cached in SQLite keyed by
the full query, and cache hits are served without a network call, which makes back
navigation and repeated queries free. The page after the one being viewed is prefetched.

All of this sits behind a search provider interface within the core, so that a caching
proxy or an owned index could replace the direct implementation later without the
renderer changing. That interface is a hedge against the rate-limit risk noted below, not
a plan.

429 responses are surfaced to the user as throttling with a retry time, not as a generic
failure.

### Staging, downloading and eviction

Auditioning a Sound streams its Preview and simultaneously enqueues its Original for
download (ADR-0003). The download queue enforces a concurrency limit and cancels
in-flight staging when the user moves past a Sound quickly, so that skimming does not
queue dozens of files.

A Staged file is a complete Original on disk with no `library_entries` row. Saving creates
that row and the file is untouched — promotion is a database write, not a file move, and
is therefore instant.

Staging is bounded by a byte budget and evicted least-recently-accessed-first. Eviction
never touches a Sound with a `library_entries` row, and never removes a file that a drag
has produced a hardlink to.

Downloads retry a small number of times on transient failure with backoff, then surface a
permanent failure on the Sound's row.

### Drag-out

Only an Original present on disk — Staged or in the Library — may be dragged. A Preview
must never be handed to `DragHost` under any circumstances; this is the single most
important invariant in the application (ADR-0003).

Because the content store names files by id, the store path is never dragged directly.
On drag start the core hardlinks the file into a temporary directory under a sanitised
filename derived from the Sound's name — the user's custom name if they set one, the
Freesound name otherwise — preserving the original extension, and hands *that* path to
`DragHost`. Collisions within the temp directory are disambiguated. Hardlinking means the
dropped file survives later eviction of the staged original, and costs no disk space.

The drag icon is the Sound's waveform.

Single-Sound drag is the primary, guaranteed gesture. Multi-Sound drag is offered only on
platforms where it has been verified to deliver every file (ADR-0001, noting the known
Windows defect); where it has not, the interface does not offer it.

Attempting to drag a Sound whose Original is not yet on disk is refused with a visible
explanation. It never silently starts a drag that will deliver nothing, and never
substitutes a Preview.

### Waveforms

Search results use Freesound's pre-rendered waveform images, recoloured to the app's
palette via CSS masking. They cost no CPU and are available before any download.

Sounds on disk get real peak data computed once in a worker thread from the decoded
Original, stored as a blob in SQLite, and rendered to canvas — supporting a sample-accurate
playhead, click-to-seek, and sharp rendering at any width. Peak computation never blocks
the interface.

### Attribution

License is stored on the Sound, carried in the sidecar, and displayed on every surface
where a Sound appears.

An Attribution Manifest is generated for a Collection and is a snapshot: it is rendered
from the Collection's membership at the moment of generation and is not a live view. It
groups Sounds by whether attribution is required, gives title, author, License name and
Freesound URL for each, and lists separately any Sound whose License restricts commercial
use. It can be copied to the clipboard or written to a file.

## Testing Decisions

### What makes a good test here

A test drives the core's command API and asserts on observable outcomes: what a
subsequent query returns, what appears on disk, and what was handed to `DragHost`. It
does not reach into the core's internals, assert on which private methods were called, or
depend on the shape of the database schema beyond what a command returns.

The bar is that a test should survive a rewrite of the module it covers, and should fail
if — and only if — a user-visible promise is broken.

### Where the tests attach

**One primary seam: the core's command API.** Tests construct the core in-process with no
Electron, injecting a fake `FreesoundGateway` and a recording `DragHost`, and pointing it
at a temporary directory and a temporary SQLite database.

`FreesoundGateway` is faked with recorded fixtures, and must be able to produce: normal
search responses, empty results, paginated results, preview streams, Original bytes, slow
and cancelled downloads, 401s, 429s, and network failures.

`DragHost` records every call so that tests can assert on the path, filename and icon the
application handed to the operating system.

**SQLite and the filesystem are real.** They are fast enough, and eviction, hardlinking,
sidecar rebuild and cache invalidation have no meaning against fakes — those are precisely
the areas where the bugs will be.

**A second, small seam: the Worker.** Tested as HTTP in, HTTP out, against a fake
Freesound token endpoint. It covers code exchange, refresh, rejection of malformed
requests, and the guarantee that `client_secret` never appears in a response.

**No renderer component tests and no Playwright suite.** React components are kept thin
enough over the core that testing them separately would add seams without adding
confidence. This is a deliberate choice to be revisited only if UI regressions actually
start escaping.

### What gets tested at the primary seam

Auth: sign-in stores an encrypted refresh token; proactive refresh occurs before expiry;
a 401 triggers exactly one refresh and one retry; a failed refresh signs out cleanly
rather than looping; signing out preserves the Library.

Search: input debouncing collapses rapid queries into few requests; a repeated query is
served from cache with no gateway call; a result page costs one gateway call regardless
of size; 429 surfaces as throttling.

Staging: auditioning enqueues a download; moving on quickly cancels it; concurrency is
capped; exceeding the budget evicts least-recently-used first; eviction never removes a
Library Sound; a Sound becomes draggable once its Original lands.

Library: saving promotes a Staged Sound without moving the file; saving is idempotent;
deleting removes both row and file; a Sound already in the Library is reported as such in
search results.

Drag-out, which carries the load of ADR-0002 and ADR-0003: the path handed to `DragHost`
has a human-readable basename derived from the Sound; it is a hardlink to the content
store, not a copy and not the store path itself; it is the Original and never a preview
URL; the hardlink still resolves after the staged original is evicted; colliding names are
disambiguated; a drag requested before the Original is present is refused rather than
served a Preview.

Recovery: deleting the database and rebuilding reconstructs the Library from sidecars
alone; a sound file present without a sidecar is reported rather than silently dropped.

Attribution: a Manifest lists every Collection member with author, License and URL;
CC0 Sounds are separated from those requiring credit; non-commercial Sounds are flagged;
the Manifest does not change when the Collection changes afterwards.

### What cannot be tested automatically

**Drag-out into real applications.** No automated test can assert that Logic Pro received
a file. This is verified manually against Logic Pro, Audacity, Final Cut, Ableton Live and
the system file manager, on both macOS and Windows. It is the Day-1 gate for the project
and a checklist item for every release. The automated suite proves the app hands the right
path to the OS; only a person can prove the OS delivered it.

### Prior art

There is none — this is a greenfield repository. These conventions are being established
here, and later work should follow them rather than introduce a second style.

## Out of Scope

- **Syncing the Library between devices.** The Library is per-device by definition
  (CONTEXT.md). A user who saves a Sound on their laptop will not find it on their
  desktop. The mandatory sidecar files leave a folder-sync approach open later without a
  schema change, but nothing in v1 addresses it.
- **Writing to Freesound.** No uploading, rating, commenting, bookmarking, or editing of
  packs. The app is read-and-download only, and the Worker exists solely to exchange
  tokens.
- **Freesound bookmarks and packs as first-class concepts.** Collections are local and
  unrelated to anything server-side.
- **Audio editing.** No trimming, normalising, pitch shifting, format conversion or
  rendering. The Original is delivered exactly as its author uploaded it.
- **Similarity search, geotagged search, and content-based descriptor queries.** The API
  supports these; v1 does not expose them.
- **Embedding attribution into audio file metadata** (BWF/iXML/ID3). The sidecar and the
  Manifest carry attribution in v1; writing it into the file itself is deferred.
- **Nested Collections.** Collections are flat and unordered.
- **Linux.** macOS and Windows only.
- **Any owned search index or caching proxy.** Search goes directly to Freesound. The
  provider interface exists so this could change; nothing is built.
- **Telemetry and crash reporting.**
- **Collaboration, sharing, or any multi-user feature.**

## Further Notes

### The risk that invalidates this spec

Freesound's documented rate limits are 60 requests per minute and 2000 per day, and the
documentation does not state whether they are counted per `client_id` or per user access
token. **If they are counted per `client_id`, every user of the application shares a single
2000/day budget and the product described here cannot exist.** This must be confirmed with
the Freesound administrators before the authentication work begins. It is the only open
question that invalidates the design rather than inconveniencing it.

The direct-to-Freesound search decision, and the provider interface that abstracts it, are
both shaped by this uncertainty.

### Build order

The drag-out spike comes first and gates everything: a throwaway Electron application with
one hardcoded audio file, dragged into Logic Pro, Audacity, Final Cut, Ableton Live and the
system file manager, on macOS and Windows, with multi-file behaviour verified. No product
code is written until it works. It is the only requirement in this document with no
workaround.

Thereafter: application shell with search and Preview playback on token auth alone — which
yields a genuinely browsable app before any auth machinery exists, and is where
responsiveness should be tuned against real data; then authentication and the Worker; then
staging and real drag-out; then the Library. Collections, the Attribution Manifest, License
filters, signing, notarization and the updater follow v1.

### Things that will be tempting and are wrong

Dragging the Preview to avoid making the user wait, intending to swap in the Original
afterwards, is forbidden (ADR-0003). The receiving application copies the file on drop, so
the swap always arrives too late, and the user ships lossy audio in finished work without
ever being told. It is the worst failure available to this application, and it is
attractive precisely because it makes the interaction feel faster.

Similarly, allowing logic to accumulate in the Electron main process rather than the core
will quietly dissolve the single test seam this spec depends on. If a behaviour cannot be
exercised without launching Electron, it is in the wrong place.
